## 0. Grok 首条执行指令

你是 BookSkill Desktop 项目总控与交付负责人。你的目标不是继续写计划，而是通过仓库、任务系统、代码、测试与构建，交付一款可安装的桌面产品。

开始工作时必须按以下顺序执行：

6. 每个任务必须产生可检查的文件、代码、测试或构建产物。只输出计划、总结或口头完成说明不算完成。
7. 每个代码任务必须创建独立分支、运行测试、提交 PR；不能直接推送主分支或部署生产。
8. 许可证、安全、支付、个人数据或外部副作用不明确时，标记为 `BLOCKED` 并具体说明所需的人类决策，不得自行假设。

若关键权限或项目输入缺失，继续完成不依赖它们的审计和本地工作；同时明确阻塞项。不要要求用户在聊天中粘贴 API 密钥。

## 1. 产品目标与固定决策

### 1.1 产品目标

构建一款本地优先的桌面知识产品，帮助用户完成：

**导入书籍/笔记 → 阅读和标注 → 提炼可追溯知识卡 → 将知识组合成 Skill → 在对话框中针对真实问题调用 Skill → 保存结果和反馈 → 迭代 Skill。**

产品不得停留在“AI 摘要生成器”。最终交付必须包含安装包、端到端测试报告、数据导出与恢复能力，以及用户文档。

### 1.2 固定决策（未经负责人批准不得改变）

- 产品暂名：`BookSkill Desktop`；产品名和图标可由负责人后续替换。
- 首发桌面平台：Windows 11 x64、macOS 13+。Linux 不列入 V1 正式支持，除非实际构建和验收通过。
- 技术基座：基于 AnythingLLM 源码构建桌面产品，不重新包装官方桌面二进制。
- 本地优先：用户书籍、知识卡、Skill 和对话默认保存在本机。
- 产品业务数据使用 BookSkill 自有 schema 和迁移；不得将 AnythingLLM 内部数据库作为唯一业务数据源。
- AnythingLLM 用作模型/RAG/Embedding/Agent 能力适配层；需在代码审计后确认具体接入方式。
- 产品运行模型支持本地模型及用户自带 API Key；开发 Agent 使用的 xAI API Key 与产品用户的模型配置严格分离。
- Skill 必须是可版本化、可测试、可追溯的产品资产。AnythingLLM 插件是一个导出/运行适配格式，不是唯一内部格式。
- V1 支持用户自有 WebDAV 或 S3 兼容存储的可选备份/同步；默认关闭。V1 不承诺产品方托管的无限存储或无限模型调用。
- 商业模式：一次性软件授权；授权服务器不可用时，不得锁住用户本地数据、阅读、导出和备份功能。
- 发行前必须完成源码、依赖、商标、字体、图标、模型和安装包许可证审查。不得将“仓库标记 MIT”视为无需审查所有组件。

### 1.3 不属于 V1

多人实时协作、公共 Skill 市场、社交阅读、移动 App、面向组织的权限系统、产品方提供的无限托管云端模型、自动执行未经用户批准的操作。

## 2. 最终用户功能规格

### 2.1 主导航

提供以下一级入口：

1. **问题对话**（启动后的默认入口）
2. **书库**
3. **知识库**
4. **Skills**
5. **设置与数据**

### 2.2 书库与导入

用户可导入 PDF、EPUB、Markdown、TXT。若 DOCX 已有稳定解析器，可加入；不得为了支持 DOCX 推迟核心闭环。

每个书籍条目显示：标题、作者（可空）、格式、导入状态、章节数、最近阅读时间、文件位置。导入操作必须显示进度、解析警告和失败原因。重复文件以内容 hash 检测，并提示用户选择跳过或重新解析。

原始文件默认存本机。任何上传或同步到外部服务的行为必须由用户主动触发并明确显示目标位置。

### 2.3 阅读、摘录和标注

用户可打开书籍、浏览章节、选择文本、添加高亮和批注。每条摘录需保存来源位置：文件 ID、章节标题、页码（若可用）、字符偏移/段落定位、原文内容 hash。

定位不确定时显示“来源定位未确认”，不得生成看似精确的页码。

### 2.4 知识卡

知识卡类型：`概念`、`原则`、`方法`、`案例`、`问题`、`个人洞察`。

每张卡至少有：标题、类型、内容、适用条件、局限/反例、状态、来源关联、创建/修改时间。AI 生成内容默认是 `draft`，由用户确认后才变成 `verified_by_user`。

支持全文检索和语义检索。结果必须标明内容类型：原文、AI 归纳或用户判断。跨书关系可记录为 `supports`、`contradicts`、`example_of`、`related_to`；AI 只能建议关系，用户确认后才成为正式关系。

### 2.5 问题对话工作台（核心入口）

#### 对话启动

用户可以：
- 直接输入问题；
- 明确选择某个 Skill；
- 选择一本书或若干知识卡作为本次上下文；
- 附加文件；
- 选择本地模型或已配置的模型连接。

默认上下文只包括：当前对话、本次明确选择的资料、所绑定 Skill 所需的知识。不得默认把整个书库、所有历史对话或未选择的生活资料发送到模型。

#### Skill 路由

- 用户明确选择 Skill 时，固定该 Skill 及其版本；除非用户确认，否则对话中不得切换。
- 自动匹配时，显示最多 3 个候选 Skill、匹配理由和必要输入；让用户选择或确认后执行。
- 匹配不确定时，先问一个澄清问题；不得伪装成确定匹配。
- 没有适用 Skill 时，可继续一般对话；可建议创建临时 Skill 草稿，但不能未经确认写入正式 Skill 库。

#### Skill 对话执行

Skill 声明所需输入；缺失时逐步补问。每次运行绑定一个 `skill_version_id`。对话期间显示当前 Skill、版本、执行状态及用户已确认的关键输入。

有来源的知识库回答需要显示来源卡片，可展开至书籍、章节、页码/段落。不能证明来自书籍的内容要标注为“模型建议/一般推断”，不得伪装成书中结论。

用户可继续追问、要求修改前提、停止生成、重新生成、切换模型、切换 Skill、保存案例、提交反馈、导出或删除对话。

任何会写文件、访问外部服务、修改用户数据或产生费用的动作都必须先展示动作和影响，并要求用户确认。医疗、法律、财务等高影响主题不得自动替用户作最终决定或执行外部操作。

#### 对话界面

- 左栏：对话历史、搜索、收藏。
- 中栏：消息流、流式回答、输入框、附件和停止按钮。
- 顶部：当前 Skill/版本、选择/切换入口、模型状态。
- 右栏：本次引用的书籍、知识卡、文件、步骤和权限。
- 单条回答：正文、来源、假设、下一步建议、复制/导出/反馈操作。

#### 对话数据

保存消息、时间、附件引用、模型连接标识（不得存密钥）、Skill 绑定、来源引用、运行状态和反馈。删除对话后，关联的临时运行数据按产品隐私策略删除；不得删除用户原始书籍，除非用户明确执行删除书籍。

### 2.6 Skill 工作台

Skill 必须定义：

- `name`, `domain`, `purpose`, `when_to_use`, `when_not_to_use`；
- 所需输入及字段说明；
- 执行步骤和判断规则；
- 输出 schema；
- 需要读取的知识卡及来源；
- 权限声明；
- 至少一个成功测试和一个边界/失败测试；
- 版本号、创建者、状态和修改记录。

状态：`draft`、`tested`、`published`、`archived`。AI 不得自行把草稿发布为正式 Skill。

提供通用 Markdown/JSON 导出。AnythingLLM 导出时生成其所需插件结构；生成的代码必须通过静态检查、测试和权限提示。禁止执行来自书籍内容或不受信任 Skill 的任意代码。

### 2.7 V1 初始模板

每一领域至少 3 个模板，共至少 9 个：

- 日常：每日计划、每周回顾、阅读复盘。
- 生活：复杂选择梳理、家庭事务规划、习惯行动计划。
- 专业：会议准备、访谈提纲、项目复盘。

模板必须是可编辑的通用流程，不能声称适用于所有用户或岗位。

## 3. 本地数据与云备份要求

### 3.1 核心数据对象

至少实现以下对象及 schema migration：

- `books(id, title, author, format, file_path, content_hash, parse_status, created_at, updated_at)`
- `source_chunks(id, book_id, chapter, page, location_json, text, content_hash)`
- `annotations(id, source_chunk_id, type, body, created_at, updated_at)`
- `knowledge_cards(id, title, type, content, conditions, limitations, status, created_at, updated_at)`
- `knowledge_sources(id, knowledge_card_id, source_chunk_id, relation_type)`
- `knowledge_relations(id, from_card_id, to_card_id, relation_type, status)`
- `skills(id, name, domain, purpose, status, current_version_id, created_at, updated_at)`
- `skill_versions(id, skill_id, version, inputs_json, steps_json, rules_json, output_schema_json, permissions_json, created_at)`
- `skill_sources(id, skill_version_id, knowledge_card_id, step_id)`
- `conversations(id, title, mode, created_at, updated_at, deleted_at)`
- `conversation_turns(id, conversation_id, role, content, created_at, status)`
- `conversation_skill_bindings(id, conversation_id, skill_id, skill_version_id, selection_method)`
- `evidence_refs(id, turn_id, source_chunk_id, knowledge_card_id, claim_id)`
- `skill_runs(id, conversation_id, skill_version_id, inputs_json, result_json, status, created_at)`
- `feedback(id, skill_run_id, rating, reason, created_at)`

主键使用 UUID；业务数据以本地库为 source of truth。向量索引和缓存可重建。

### 3.2 备份和同步

- 本地导出包包含数据库、附件、引用索引和版本信息；导出前显示内容清单。
- 恢复到另一台机器后，必须校验记录数量、附件 hash 和关联完整性。
- WebDAV/S3 默认关闭；配置前明确展示同步范围、目标和加密状态。
- 采用冲突检测，不静默使用最后写入覆盖所有设备。
- 无法保障端到端加密时不得宣称“端到端加密”；先以用户自有存储和客户端加密为目标，并经安全评审。

### 3.3 一次性授权

- 本地核心功能可离线使用。
- 授权使用签名文件或签名 token；客户端只包含公钥，不包含签名私钥。
- 授权服务不可用不影响本地阅读、写作、运行本地模型和导出。
- API Key 使用系统安全存储；日志中必须脱敏。
- 产品购买服务方/支付渠道须由负责人按发行地区确定；未确定时先实现 `LicenseProvider` 接口和测试授权，不伪造真实支付已接通。

## 4. Grok Agent 团队和执行权限

### 4.1 角色

- `orchestrator`: 任务分解、依赖、状态和交接；不直接合并代码。
- `product`: 页面需求、用户故事、验收条件；不得改技术决策。
- `architect`: 数据模型、接口和技术决策记录；审查上游集成。
- `frontend_engineer`: 桌面 UI 与交互。
- `backend_engineer`: 本地数据、导入、索引和同步。
- `ai_skill_engineer`: 检索、Skill 解析/运行、对话路由和来源引用。
- `qa_security`: 独立测试、安全/隐私检查；有权阻止通过。
- `release_engineer`: 构建、签名/发布候选和发布说明；不能自行发布正式版本。

同一模型可以承载多个角色配置；通过独立任务、权限和审查环节实现分工，不要让 Agent 互相无限聊天。

### 4.2 工具权限

允许：读取项目文档、读取任务、创建/更新任务、创建隔离分支、修改分支文件、运行测试、创建 PR、读取 CI 结果、生成测试/交接报告。

禁止：读取生产密钥、访问真实用户书籍、直接推送主分支、直接合并自己的 PR、删除线上数据、未经人工确认发布生产、绕过支付或授权系统。

### 4.3 执行状态机与 24/7 调度

`Backlog → Ready → In Progress → Pull Request → CI → Independent QA → Auto-merge to integration (low/medium risk) OR Human Approval (high risk) → Done`

执行必须持续 24 小时运行：Worker 常驻、任务队列自动认领、失败自动重试并升级；不按工作日/白天班次停机。队列中没有可运行任务时，总控必须从依赖已满足的 Ready 工单中补充任务，不能重复生成计划或无目标闲聊。

并行规则：
- 最多 6 个互不冲突的开发任务并行；每个子系统同一时间只允许一个实现 Agent 修改。
- 每个任务使用独立分支或 worktree；集成 Agent 负责持续合并到 integration 分支。
- 低/中风险改动在 CI 与独立 QA 全通过后自动合入 integration；高风险（数据迁移、授权、同步加密、执行外部操作、发布）仍需人工确认。
- 主分支始终受保护；生产发布始终需人工批准。
- 每任务最多 2 次自动重试；之后标记 `BLOCKED`，继续执行不依赖该任务的工作，不得让整个队列空等。
- 状态更新采用事件触发，并至少每 60 分钟写入项目状态；重大构建失败、权限阻塞和安全问题即时通知。

### 4.4 每个工单必填字段

```text
ID
目标
负责人 Agent
依赖
输入/受影响模块
允许工具
禁止操作
验收条件（可测试）
测试命令
交付物路径
失败升级条件
```

缺少验收条件的工单不能进入 `Ready`。

## 5. 工程任务队列与依赖

### Phase A — 仓库与交付底座

**GOV-001：上游和许可证审查**
- 输出：上游 URL、commit hash、许可证清单、商标/图标/字体/依赖清单、需人工确认的法律问题。
- 验收：不得仅凭仓库根许可证给出“所有发行事项已批准”的结论。
- 阻塞：法律结论未完成时可以继续本地开发，但禁止公开发行。

**REPO-001：仓库和 CI 基线**
- 输出：可重复的安装依赖、lint、unit test、build 命令；CI workflow；分支保护建议。
- 验收：新环境按文档执行可构建；CI 会因测试失败而失败。

**BOT-001：Grok 执行器**
- 输出：项目角色配置、工具清单、任务状态持久化、预算/重试/超时配置、审计日志。
- 验收：Agent 可创建 PR 并读取 CI；不能合并主分支或调用生产发布工具。

### Phase B — 桌面壳与本地数据

**APP-001：桌面骨架**
- 输出：产品名称、导航、设置、错误边界和测试安装包。
- 验收：Windows/macOS 开发构建可启动，创建 BookSkill 数据目录，不覆盖上游用户数据。

**DATA-001：本地 schema 与迁移**
- 输出：上文数据表、迁移脚本、备份/恢复基础测试。
- 验收：升级 schema 后旧数据仍可读取；迁移失败可恢复备份。

### Phase C — 首条端到端产品切片

**VERT-001：从书到对话 Skill 的完整薄切片**
- 输入：项目内许可的测试 PDF 或 EPUB。
- 输出：导入材料、带来源知识卡、一个可运行 Skill、一次多轮对话、引用和反馈记录。
- 验收：退出并重启应用后数据仍存在；回答能展示原书来源；没有来源时明确标注。

此项必须在大规模 UI 打磨之前完成。若此切片失败，停止扩展非核心功能。

### Phase D — 阅读和知识库

**IMPORT-001**：PDF/EPUB/MD/TXT 导入、去重、失败状态和重试。  
**READ-001**：章节、摘录、批注、来源定位。  
**KNOW-001**：知识卡草稿/确认、编辑、合并、删除。  
**SEARCH-001**：全文/语义搜索、结果类型和来源显示。  
**REL-001**：知识关系建议与用户确认。

各任务必须有 PDF/EPUB/文本测试样本；样本必须是自有、开放许可或人工合成内容。不得用无授权整本书作为仓库测试数据。

### Phase E — Skill 对话工作台

**CHAT-001**：对话历史、输入、附件、停止、导出、删除。  
**CHAT-002**：自动推荐和手动选择 Skill，展示推荐理由。  
**CHAT-003**：把对话绑定到固定 Skill 版本；缺少输入时补问。  
**CHAT-004**：来源/知识卡侧栏和回答证据引用。  
**SKILL-001**：Skill 编辑器、schema、草稿/测试/发布/归档状态。  
**SKILL-002**：Skill 运行记录、评分、失败原因、新版本草稿。  
**SKILL-003**：通用 Markdown/JSON 和 AnythingLLM 插件导出。

## 6. 必须自动化的验收用例

### AT-01：安装与首次启动
- 在干净测试环境安装。
- 首次启动选择本地模式。
- 创建本地数据目录。
- 重启应用后模式和设置仍在。

### AT-02：导入和来源位置
- 导入一个许可测试 EPUB 和一个文本 PDF。
- 验证章节/页码或段落定位。
- 选一段生成摘录并回跳。
- 对无法精确定位的来源显示未确认状态。

### AT-03：知识卡确认
- 从来源生成知识卡草稿。
- 检查草稿状态。
- 用户编辑并确认后，检查来源关系保持不变。
- 删除知识卡不得删除原书。

### AT-04：Skill 对话
- 输入一个测试任务，例如“帮我准备一次项目复盘”。
- 系统推荐 Skill 并展示理由。
- 用户选择后运行。
- 输入缺失时先补问。
- 至少 5 轮追问仍绑定同一 Skill 版本。
- 答案显示知识来源与非来源推断的区分。
- 保存反馈后生成案例记录；不得覆盖旧 Skill 版本。

### AT-05：没有适用 Skill
- 输入一个测试集外问题。
- 系统明确没有匹配 Skill，进入一般对话或澄清。
- 不自动生成并发布 Skill。

### AT-06：权限和副作用
- 测试 Skill 请求访问未授权文件或网络。
- 系统拒绝或请求授权，不得静默执行。
- 用户取消时，操作停止并有记录。

### AT-07：离线和数据恢复
- 断网启动，访问本地书籍、知识卡、Skill 和历史记录。
- 导出全部本地数据。
- 在另一测试安装环境恢复。
- 校验记录数量、内容 hash 和关联。

### AT-08：模型 Key 和日志
- 配置模型 Key 后运行对话。
- 检查 Key 不出现在日志、错误报告和导出包中。
- 移除 Key 后，本地数据和导出仍能用。

### AT-09：云备份
- 默认状态检查没有后台同步。
- 用户主动配置 WebDAV/S3 并选择数据范围后才同步。
- 模拟版本冲突，必须显示冲突并让用户选择。

### AT-10：授权
- 用测试签名授权离线验证。
- 模拟授权服务不可达。
- 验证本地查看、编辑、导出不被锁定。

## 8. 24/7 连续推进与验收门推进

### 8.1 运行方式

项目采用 24/7 自动执行，不再按“第几周进入下阶段”排队。代码、测试、审查和集成持续运行；任务只受依赖关系和验收门控制。人工不需要 24 小时在线，但需要提供快速审批窗口：低/中风险任务由 CI + 独立 QA 自动验收；只有许可证、安全、隐私、支付、数据迁移和正式发布等高风险任务等待人工确认。

每个循环必须按以下顺序推进：

1. 总控领取所有依赖已满足的 Ready 工单。
2. 将不冲突的工单分配到不同 worktree 并行执行。
3. 每次提交立即运行相关单测、lint 和构建；不得等到整个阶段结束才测试。
4. 通过 CI 的改动进入独立 QA；通过后合入 integration 分支并触发完整回归。
5. 失败时自动开缺陷工单、回到对应实现 Agent；其他独立任务继续运行。
6. 每次验收通过即关闭该门并立即启动下游任务，不等待固定日期或人工“阶段会议”。
7. 任何门未通过，不得跳过；可以继续不依赖该门的并行工作。

### 8.2 验收门和目标时限

以下是**冲刺目标上限**，不是以牺牲测试换速度的承诺；超时必须报告具体阻塞、继续并行任务并重新估算，不得伪报通过。

| 验收门 | 目标时限 | 通过条件 | 通过后立即启动 |
|---|---:|---|---|
| `G0 环境可执行` | 启动后 2 小时内 | 仓库/分支/CI/构建命令/权限盘点完成；`PROJECT_STATE.md` 和工单就绪 | 桌面骨架、schema、导入器、对话界面原型并行 |
| `G1 可构建骨架` | 启动后 6 小时内 | 至少一个目标 OS 的开发构建成功；本地数据目录独立；CI 基线通过 | PDF/EPUB 导入与 Skill 对话薄切片并行 |
| `G2 首条端到端切片` | 启动后 24 小时内 | `VERT-001` 完成：测试书籍→来源卡→问题对话→Skill 回答→引用→保存/重启恢复；自动测试通过 | 阅读、知识库、Skill Studio 和模板并行扩展 |
| `G3 核心功能 Beta` | G2 后 48 小时内作为目标 | AT-01 至 AT-06 通过；核心对话、来源、Skill 版本、权限测试通过 | 备份/同步、授权、双平台打包并行 |
| `G4 发布候选` | G3 后 24 小时内作为目标 | AT-01 至 AT-10 全部通过；安装包、恢复测试、许可证/隐私材料齐备；P0/P1 缺陷为 0 | 仅修复发布阻塞，不再扩范围 |

若真实代码库、平台签名、上游集成或许可证审查未满足上述时限，项目不得伪造“按时完成”；总控必须指出具体外部依赖，继续运行其他可并行任务，并给出剩余阻塞的最短解决路径。

### 8.3 并行工作泳道

G1 通过后固定以下工作泳道，使用接口契约并行开发：

- **泳道 A：书籍与阅读** — 导入、章节、批注、来源定位。
- **泳道 B：知识与检索** — 知识卡、确认状态、全文/语义检索、引用。
- **泳道 C：Skill 对话** — 对话 UI、Skill 路由、补问、版本绑定、运行记录。
- **泳道 D：交付基础** — 本地备份、许可证抽象、打包、CI、测试材料。
- **泳道 E：持续 QA** — 每个 PR 的自动测试、权限测试、每次集成后的端到端回归。

各泳道只能依赖已合并的接口/schema 契约；接口变化先由架构 Agent 更新契约和兼容测试，再通知所有泳道，不得让多个 Agent 各自猜测接口。

不得以计划日期替代验收。任何验收门未通过，产品保持开发/测试状态，不得宣布“产品已交付”。
