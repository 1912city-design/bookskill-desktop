## 设计约束

1. **追加历史，不改写历史行。** 回滚 = 读取旧快照，写入一条新的当前版本/修订，并把当前指针指向它。不得 DELETE 或 UPDATE 已存在的 `skill_versions` 内容字段，也不得改写已存在的知识卡修订行。
2. **D-018**：回滚或新建版本不得自动把 Skill 设为 `published`。若当前是 `published`，回滚后的状态规则：新版本先进入 `draft` 或保持用户显式指定的非 published 默认（`draft`），由用户再次发布。测试必须覆盖“回滚不会自动发布”。
3. **D-017**：知识卡回滚只恢复 title / content / conditions / limitations 等正文字段，**不得**因回滚自动把 `status` 改为 `verified_by_user`。与 `updateKnowledgeCard` 一样，状态保持回滚前的状态，除非走既有 `confirmKnowledgeCard`。
4. **合并/删除契约**（P-012）不变。删除知识卡时必须清理其修订行，避免外键悬空。合并时在幸存卡上追加一条修订（记录合并后的内容），被吸收卡的修订随删除清理；不为此改 `knowledge_relations`。
5. 版本历史不是整库备份，不得把 BACKUP-001 范围做进本票。

## 建议 schema（V3，名称可微调，但必须有测试与迁移）

```
knowledge_card_revisions (
  id TEXT PRIMARY KEY,          -- UUID
  card_id TEXT NOT NULL,        -- FK knowledge_cards(id)
  revision INTEGER NOT NULL,    -- 每张卡从 1 递增
  title TEXT NOT NULL,
  type TEXT NOT NULL,
  content TEXT NOT NULL,
  conditions TEXT,
  limitations TEXT,
  status TEXT NOT NULL,         -- 该快照被写下时的状态（只记录，回滚不自动套用为确认）
  created_at TEXT NOT NULL,
  UNIQUE (card_id, revision),
  FOREIGN KEY (card_id) REFERENCES knowledge_cards(id)
)
```

现有库升级后，应为每张已有知识卡补写 revision=1 的基线快照（等于当前行）。随后 `draftKnowledgeCardFromLocator` / `updateKnowledgeCard` / `confirmKnowledgeCard` / `mergeKnowledgeCards` 都必须追加修订。`SCHEMA_VERSION_CURRENT` 改为 3。旧数据必须仍可读取（DATA-001 验收精神）。

Skill 侧不强制新表：补齐并测试：

- `listSkills(db)`
- `listSkillVersions(db, skillId)`（按创建时间/版本排序）
- `rollbackSkillToVersion({ db, skillId, versionId })`：把目标历史版本的 inputs/steps/rules/output/permissions/来源复制为**新的** `skill_versions` 行（新 UUID，新 version 号，例如从 `1.0.0` 递增或使用 `1.0.0+rollback-<shortid>` 一类可追溯编号），`current_version_id` 指向新行；旧行全部保留。
- 可选：`updateSkillMetadata`、`transitionSkillStatus`（拒绝 AI/默认路径写入 `published`；`published` 只能由显式用户向 API 传入，且测试覆盖默认拒绝）。

## 验收条件（可测试）

1. **Skill**：创建 Skill 后改一版，`listSkillVersions` 至少 2 条；回滚到第一版后，当前指针的内容等于第一版快照，且历史行仍在（至少 3 行：v1、v2、回滚产生的新行）。回滚不自动 `published`。
2. **知识卡**：创建草稿、编辑、确认后，修订列表长度递增；回滚到编辑前的内容后，正文恢复，status 不自动变为 `verified_by_user`（若回滚前已是确认状态，也不得悄改变成另一种状态；只恢复正文）。再确认仍走 `confirmKnowledgeCard`。
3. **迁移**：V2 库（含已有知识卡）应用 V3 后可读取，且每张卡至少有 1 条基线修订。迁移失败路径不弱于既有 DATA-001 备份行为。
4. **删除**：删除知识卡后，其修订行不再残留；原书与 source_chunks 仍在。
5. 自动化测试覆盖上述路径及“回滚不改写旧行”；失败时非零退出。独立 QA 通过后，将结果交 Orchestrator，等待人工确认再合入 `integration`。不得宣布完成，除非独立 QA 验证通过（合入另计）。
